# CareerOS Infinity: engineering review and fixes

Reviewed on 27 September 2026. Base commit: `382263a95eb60489c41dafe5b35b666b83561605`.

## Assessment

CareerOS has useful building blocks: a FastAPI service layer, typed database models, a Next.js interface, explicit application states, and resume provenance concepts. Its current maturity is a **prototype**. The largest gaps are authentication, reliable state transitions, ownership of records, and UI claims that exceed the underlying implementation.

The best next investment is one complete, reproducible workflow: sign in → upload a resume → retrieve an actual job → prepare a grounded application → record user approval → retain submission evidence. Adding more portal names before that workflow is verified will increase maintenance without establishing reliability.

## Remaining priorities

1. **Make clean database setup reproducible.** The first Alembic revision has no parent but alters `resumes` without creating its baseline. The checked-in migrations also do not establish all runtime tables such as refresh tokens, audit logs and graph nodes. Validate migrations from an empty PostgreSQL/pgvector database before deployment. Do not paper over this by silently skipping database errors.
2. **Finish the real profile and matching workflow.** The profile page is a preview; job-detail scores, keywords and generated text are illustrative. Connect them to authenticated profile/resume APIs and the stored job description. Scores elsewhere in `jobs.py` and `jobpilot.py` still include hardcoded assumptions.
3. **Unify application storage and evidence.** Relational `Application` records and graph records have different lifecycle paths. Email matching is still based on company text in a subject, which can confuse two applications at the same company. Use application-specific receipt identifiers, timestamps, sender checks and durable audit evidence. The graph email-verification endpoint does not yet handle relational applications.
4. **Replace prototype automation claims.** `BrowserAutomationService.run_auto_apply` currently prepares records; it does not perform a verified external submission. Other adapter/service paths contain simulations. The voice agent still uses keyword routing and can label failures as “healed.” Establish actual integration tests per supported portal before claiming live support.
5. **Complete deployment and session hardening.** GitHub Pages workflow expects `frontend/out`, while Next is configured for a server build and has dynamic routes. Use an appropriate Next.js server deployment or redesign for static export. Add login throttling, refresh-token rotation/storage hashing, a deliberate cross-site cookie policy, and authenticated websocket behavior. JWT and vault keys should be separated with a planned vault re-encryption procedure.
6. **Improve test and dependency discipline.** Several existing tests check constants or in-memory examples rather than the feature named by the test. Pin tested dependencies, add clean-database migration tests, validate actual account isolation against PostgreSQL, and build controlled browser fixtures. Remove tracked bytecode/build metadata in a separate cleanup.

## Upgrade notes

- Generate and configure a private `SECRET_KEY` before starting. Previously issued access tokens will no longer validate after rotation.
- The existing vault derives encryption from `SECRET_KEY`. Changing it makes previously encrypted entries unreadable. Re-enter credentials under the new key; do not copy the published development key into a deployment.
- Create/sign into an actual account. Obtain its UUID from `GET /api/v1/auth/me`; explicitly configure `DESKTOP_OPERATOR_USER_ID` to enable the legacy shared desktop/vault functions for that account.
- Legacy all-zero-user data and graph nodes without ownership are **not** reassigned automatically. An administrator must establish ownership and migrate them deliberately.
- Configure `CORS_ORIGINS` as a JSON array of exact frontend origins. Set `NEXT_PUBLIC_API_URL` before building the frontend. Local HTTP development can use `COOKIE_SECURE=false`; production should use HTTPS and secure cookies.
- `/applications/apply` now returns `application_id`. The bundled frontend is updated. It prepares a record and does not claim external submission.
- This branch contains code changes only; no job applications, emails, production data changes or deployments were performed during verification.

## Verification

**Results:** 84 selected backend tests passed; 8 frontend tests passed; the Next.js production build and TypeScript checks passed. Python compilation, YAML parsing, and `git diff --check` also passed. The selected backend suite covers HTTP authentication boundaries, owner filtering, operator access, logout revocation, password behavior, preparation semantics and existing stability/sandbox regressions. Frontend tests cover metrics and API transport, followed by a production build with TypeScript checks.

Database-dependent JobPilot suites and real external browser/application workflows require dedicated infrastructure and were not run. Browser visual verification was blocked because the Chromium download returned an invalid archive. A passing build does not establish clean-database deployment or live job-portal compatibility.
